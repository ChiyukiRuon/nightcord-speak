# 音频架构

`crates/ts-audio` 拥有客户端里**每一个 PCM 采样**（§26、§80 原则 4）。

---

## 1. 数据流

```text
麦克风 ─▶ capture ─▶ 重采样 ─▶ 门限 ─▶ Opus 编码 ─▶ VoicePacket ─┐
                                                                │
                                          后端（ts-protocol-ts3）│ UDP ─▶ 服务器
                                                                │
混音缓冲 ◀── 后端抖动/解码 ◀── UDP ◀────────────────────────────┘
   │
   └─▶ playback ─▶ 扬声器
```

**收发格式不同，这是刻意的：**

| 方向 | 采样率 | 声道 | 每帧样本 |
| --- | --- | --- | --- |
| 采集（恒定） | 48000 | **2（立体声交错）** | 1920 |
| 发送 · 桌面 | 48000 | **2（立体声交错）** | 1920 |
| 发送 · 网关 | 48000 | **1（单声道）** | 960 |
| 接收（解码输出） | 48000 | **2（立体声交错）** | 1920 |

`tsclientlib` 的解码器固定输出立体声。采集**恒定**输出立体声，与发送几声道无关
——重开 cpal 流意味着把麦克风关掉一段时间，代价远大于每帧多一次降混。单声道麦克风
会被复制到两个声道；超过两声道的设备取前两路。

网关那一路是单声道，因为浏览器 worklet 送来的就是单声道。

两边都由 `ts-audio::format` 定义，跨边界一律走这些常量。

---

## 2. 职责划分：为什么抖动/解码不在这个 crate 里

§26 的模块清单里列了 `jitter.rs`、`decoder.rs`、`mixer.rs`。**实现中没有它们**，
这是有意的偏离：

- `tsclientlib` 的 `AudioHandler` 已经提供了自适应抖动缓冲、丢包补偿、
  每客户端解码队列与混音，且与它自己的包序号逻辑紧耦合。
- §77 明确说 `tsclientlib` 是**基础**而非架构；§80 原则 7 要求先能跑起来。
- 重新实现意味着重新实现大量经过调优的行为，且极难测到同等覆盖。

因此划分是：

| 层 | 负责 |
| --- | --- |
| `tsclientlib`（在 `ts-protocol-ts3` 之后） | UDP 传输、解密、抖动缓冲、丢包补偿、Opus **解码**、混音 |
| `ts-audio` | 设备、采集、重采样、**Opus 编码**、VAD、PTT、播放 |

两者之间是 `ts_protocol::AudioSink`：后端把混好的立体声帧推进去，
`ts-audio` 实现它并写进播放环形缓冲。这样 `ts-audio` **不依赖任何协议库**，
可以直接单元测试，也不受协议层变化影响。

**单人音量因此落在后端而不是 `ts-audio`**：混音发生在 `tsclientlib` 的
`AudioHandler` 里，那里每个说话人一个 `AudioQueue`，而 `AudioQueue::volume`
是公开字段。后端在自己的 `Audio` 上维护一张 `HashMap<ClientId, f32>` 覆盖表，
在**队列新建的那一刻**（`handle_packet` 报出新说话人）套用回去——因为说话人一停
队列就被删掉，只存在队列上的音量撑不过一句话。总音量则相反，它作用在混好的输出
上，所以住 `ts-audio::playback` 的一个原子量里。

如果将来要替换接收管线，`AudioSink` 就是那唯一的接缝。

## 3. 线程模型

`cpal::Stream` 在 cpal 0.18 里是 `Send + Sync`（已用编译期断言实测确认），
所以流可以随引擎移动，不需要专门的音频线程。

```text
tokio 任务            设备回调（实时约束）
   │                        │
引擎 poll() ─编码─▶ 网络    │
   │                        │
sink.push() ─▶ 环形缓冲 ─▶ 回调取用
```

播放使用**无锁 SPSC 环形缓冲**（`ring.rs`）：在音频回调里取互斥锁可能导致
优先级反转并听成断音。回调**永不阻塞**——缓冲不足时输出静音（设备缓冲本就
预填了 0），而不是等待。

## 3.5 编码：一个档位，就是最高档

**编码器没有设置。** 它永远跑在协议允许的最高码率上，libopus 永远用
`Application::Audio`（为任意音频优化，而不是为语音丢高频）。

为什么不做成可调：语音通话的质量不该是一个要用户去找的旋钮。发现音质差的人不应
该再去找一个滑块才能修好，而没发现的人本来也在为上限付带宽。代价是上行——下面
那张表就是全部代价。

TeamSpeak 把 Opus 暴露成**两次**——「Opus Voice」（单声道）与「Opus Music」
（立体声）——它们在线路上是两个不同的 codec 字节，不是一个编解码器上的旋钮。
本客户端用哪个**不取决于偏好，取决于喂进去的是什么**：

| 前端 | 采集 | 发送 | 码率 |
| --- | --- | --- | --- |
| 桌面 | 恒定立体声 | Opus Music，立体声 | 79,200 bps |
| Web 网关 | 浏览器 worklet 给的单声道 | Opus Voice，单声道 | 45,056 bps |

两个数字都取自 TeamSpeak 公布阶梯的顶端（原表 `步长 × (档位 + 1)`，Voice 步长
4096、Music 步长 7200，档位 1–10）。放在 `ts-audio::encoder`，也只有那一份——
前端显示「正在以 48 kHz 发送 Opus 立体声，约 79 kbps」时读的是 `voice_status`，
不另抄一张表。

**为什么声道数是参数而不是设置**：它是输入的性质，不是用户的偏好。网关收到的是
单声道帧，把它编成立体声等于为一个声道的信息付两次带宽。

**位深**：Opus 没有位深这个概念——它是有损编码，输入输出都是采样值。本管线全程
`f32`，而 f32 的尾数是 24 位，所以整数意义上的「24 位」已经被超过了。

## 4. 发送判定

`TransmitPolicy` 是唯一决定「这一帧发不发」的地方，且**不持有设备或编解码器**，
因此所有模式组合都能直接单元测试：

| 模式 | 行为 |
| --- | --- |
| `VoiceActivation` | 交给门限（阈值 + attack/release） |
| `PushToTalk` | 只看按键是否按下，**绕过门限**（§30）。按键由系统级热键驱动，见 [`docs/shortcuts.md`](shortcuts.md) |
| `Continuous` | 始终发送 |
| `Muted` | 从不发送 |

叠加规则：

- **输入静音优先于一切模式**——静音时按住 PTT 也不发。
- **切换模式会重置门限**，否则门限开着切到 PTT 会导致松键仍发送。
- **取消静音不会立刻开门**：门限已重置，仍需重新经过 attack，
  否则取消静音的第一帧会把房间噪声整段发出去。
- `is_resume` 只在「上一帧没发、这一帧发」时为真，供对端区分
  「重新开口」与「丢包」。

## 5. 设备错误：瞬态 vs 致命

`cpal` 报告的错误**大多数是瞬态的**。实测中一个 WASAPI buffer underrun
曾让麦克风被标记为永久失效——但之后它继续正常送帧。

现在的分类：

| 致命（结束流） | 瞬态（记日志继续） |
| --- | --- |
| `DeviceNotAvailable` | `Xrun` |
| `HostUnavailable` | `DeviceBusy` |
| `StreamInvalidated` | `DeviceChanged`（宿主已自动切换路由） |
| | `RealtimeDenied` |

设备消失时 `is_running()` 转为 false。**UI 会提示**——`nightcord_voice_status` 的
`available` / `healthy` 就是为此而设，见 [`docs/devices.md`](devices.md)。

## 6. 已知取舍

| 项 | 说明 |
| --- | --- |
| 播放设备必须支持 48 kHz | 回调里重采样意味着在回调中分配内存，因此不做。设备不支持时明确报 `UnsupportedConfig`，由用户换设备，而不是变调播放。 |
| 静音时仍解码 | 静音时 `AudioSink::space()` 返回无上限并丢弃音频。这样后端抖动缓冲保持排空；若返回 0，取消静音时会播放积压的旧音频。代价是静音期间仍消耗解码 CPU。 |
| 采集回调有分配 | 只剩成帧本身一次（`try_send` 按值收帧，而引擎在另一个线程）。此前每次回调还多两次，已随立体声改造一并去掉。 |
| 音质 | 已由用户实测确认「偏低」，本轮据此把编码固定到最高档（§3.5）。听感仍是人耳验证项，以及官方客户端能否解出立体声档（见 `AGENTS.md` §5.4）。 |
| 单人音量不持久化 | `AudioQueue.volume` 是会话内状态。官方客户端按唯一身份记住每个人的音量，那要多一个存储和一次 `ClientId → unique_id` 解析，留到下一轮。 |
