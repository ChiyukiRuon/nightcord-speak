# 音频架构

`crates/ts-audio` 拥有客户端里**每一个 PCM 采样**（§26、§80 原则 4）。

---

## 1. 数据流

```text
麦克风 ─▶ capture ─▶ 重采样 ─▶ 门限 ─▶ Opus 编码 ─▶ VoicePacket ─┐
                                                                │
                                          后端（ts-protocol-ts3）│ UDP ─▶ 服务器
                                                                │
混音缓冲 ◀── 后端抖动/解码 ◀── UDP ◀────────────────────────────┘
   │
   └─▶ playback ─▶ 扬声器
```

**收发格式不同，这是刻意的：**

| 方向 | 采样率 | 声道 | 每帧样本 |
| --- | --- | --- | --- |
| 发送（Opus 编码） | 48000 | **1（单声道）** | 960 |
| 接收（解码输出） | 48000 | **2（立体声交错）** | 1920 |

`tsclientlib` 的解码器固定输出立体声，而 TS3 语音在线路上是单声道。
两边都由 `ts-audio::format` 定义，跨边界一律走这些常量。

---

## 2. 职责划分：为什么抖动/解码不在这个 crate 里

§26 的模块清单里列了 `jitter.rs`、`decoder.rs`、`mixer.rs`。**实现中没有它们**，
这是有意的偏离：

- `tsclientlib` 的 `AudioHandler` 已经提供了自适应抖动缓冲、丢包补偿、
  每客户端解码队列与混音，且与它自己的包序号逻辑紧耦合。
- §77 明确说 `tsclientlib` 是**基础**而非架构；§80 原则 7 要求先能跑起来。
- 重新实现意味着重新实现大量经过调优的行为，且极难测到同等覆盖。

因此划分是：

| 层 | 负责 |
| --- | --- |
| `tsclientlib`（在 `ts-protocol-ts3` 之后） | UDP 传输、解密、抖动缓冲、丢包补偿、Opus **解码**、混音 |
| `ts-audio` | 设备、采集、重采样、**Opus 编码**、VAD、PTT、播放 |

两者之间是 `ts_protocol::AudioSink`：后端把混好的立体声帧推进去，
`ts-audio` 实现它并写进播放环形缓冲。这样 `ts-audio` **不依赖任何协议库**，
可以直接单元测试，也不受协议层变化影响。

如果将来要替换接收管线，`AudioSink` 就是那唯一的接缝。

## 3. 线程模型

`cpal::Stream` 在 cpal 0.18 里是 `Send + Sync`（已用编译期断言实测确认），
所以流可以随引擎移动，不需要专门的音频线程。

```text
tokio 任务            设备回调（实时约束）
   │                        │
引擎 poll() ─编码─▶ 网络    │
   │                        │
sink.push() ─▶ 环形缓冲 ─▶ 回调取用
```

播放使用**无锁 SPSC 环形缓冲**（`ring.rs`）：在音频回调里取互斥锁可能导致
优先级反转并听成断音。回调**永不阻塞**——缓冲不足时输出静音（设备缓冲本就
预填了 0），而不是等待。

## 4. 发送判定

`TransmitPolicy` 是唯一决定「这一帧发不发」的地方，且**不持有设备或编解码器**，
因此所有模式组合都能直接单元测试：

| 模式 | 行为 |
| --- | --- |
| `VoiceActivation` | 交给门限（阈值 + attack/release） |
| `PushToTalk` | 只看按键是否按下，**绕过门限**（§30） |
| `Continuous` | 始终发送 |
| `Muted` | 从不发送 |

叠加规则：

- **输入静音优先于一切模式**——静音时按住 PTT 也不发。
- **切换模式会重置门限**，否则门限开着切到 PTT 会导致松键仍发送。
- **取消静音不会立刻开门**：门限已重置，仍需重新经过 attack，
  否则取消静音的第一帧会把房间噪声整段发出去。
- `is_resume` 只在「上一帧没发、这一帧发」时为真，供对端区分
  「重新开口」与「丢包」。

## 5. 设备错误：瞬态 vs 致命

`cpal` 报告的错误**大多数是瞬态的**。实测中一个 WASAPI buffer underrun
曾让麦克风被标记为永久失效——但之后它继续正常送帧。

现在的分类：

| 致命（结束流） | 瞬态（记日志继续） |
| --- | --- |
| `DeviceNotAvailable` | `Xrun` |
| `HostUnavailable` | `DeviceBusy` |
| `StreamInvalidated` | `DeviceChanged`（宿主已自动切换路由） |
| | `RealtimeDenied` |

设备消失时 `is_running()` 转为 false。**UI 会提示**——`nightcord_voice_status` 的
`available` / `healthy` 就是为此而设，见 [`docs/devices.md`](devices.md)。

## 6. 已知取舍

| 项 | 说明 |
| --- | --- |
| 播放设备必须支持 48 kHz | 回调里重采样意味着在回调中分配内存，因此不做。设备不支持时明确报 `UnsupportedConfig`，由用户换设备，而不是变调播放。 |
| 静音时仍解码 | 静音时 `AudioSink::space()` 返回无上限并丢弃音频。这样后端抖动缓冲保持排空；若返回 0，取消静音时会播放积压的旧音频。代价是静音期间仍消耗解码 CPU。 |
| 采集回调有分配 | 每个完成帧分配一个 `Vec`。可以改成池化，但当前量级（50 次/秒）无实测影响。 |
| 音质未验证 | 帧数、时长、电平已验证；**实际听感未经人耳确认**。 |
